# Решения и допущения

ТЗ не отвечает на всё; здесь собрано то, что пришлось решать по ходу, и то, чего в работе нет.

## Модель данных и права

- **Две роли, несколько пользователей каждой.** Роль лежит в `profiles` (`manager` / `executor`),
  таблица для пользователя доступна только на чтение своей строки — повысить себя самому
  нельзя. Аккаунты создаёт админ (открытая регистрация выключена в настройках проекта).
- **Как роль появляется у нового аккаунта.** Для теста триггер `handle_new_user` берёт роль из
  локальной части email: `manager…` → постановщик, остальные → исполнитель. В реальном проекте
  роль назначал бы админ отдельным полем в дашборде — это единственное место, где правило
  «тестовое», оно помечено в миграции 0003.
- **Видимость объектов.** Постановщик видит все объекты, включая пустые. Исполнитель — только
  те, где есть хотя бы одна его задача. Объект без задач исполнителю не виден вовсе.
- **Права постановщика не привязаны к объекту.** Любой постановщик правит любой объект и любую
  задачу: в ТЗ постановщик «видит всё», разделении объектов между руководителями нет.
- **Один исполнитель на задачу.** Формулировка ТЗ («исполнитель») в единственном числе;
  несколько ответственных не делал.
- **Задача без исполнителя допустима** (создал, ещё не назначил). Статус — «Новая», никто,
  кроме постановщиков, её не видит.

## Статусы

- **Справочник переходов — таблица `task_transitions`.** Правила не зашиты в код функции:
  добавить разрешённый переход = одна строка в базе, а не правка логики. Функция
  `set_task_status()` читает этот справочник, поэтому база отклоняет переход, даже если
  запрос пришёл в обход интерфейса.
- **Смена статуса — только через `set_task_status()`.** Прямой `UPDATE tasks.status` запрещён
  на уровне привилегий к колонке, а не «не рекомендуется».
- **Комментарий обязателен только у перехода «На проверке → На доработке»**, как в ТЗ.
  Комментарий при «Отправить на проверку» не собирается — ТЗ его не требует.
- **«Принята» — финал.** Переоткрыть принятую задачу нельзя: в ТЗ такого перехода нет.
- **Сменить исполнителя можно на любом статусе.** Последствие: у прежнего исполнителя задача
  исчезает из «Моих задач» сразу, потому что доступ строится на назначении. Если это неправильно,
  правильный вариант — разрешать переназначение только в статусе «Новая».
- **Задачу нельзя переносить между объектами** (`object_id` защищён триггером). Не указано в ТЗ,
  но иначе история «задача с такой-то стройки» врёт.
- **Правка задачи** (название, описание, исполнитель) — только постановщиком. Исполнитель
  содержимое не редактирует: ТЗ разрешает ему только движения по статусам.

## История

- **Первая запись («— → Новая») создаётся триггером на вставку задачи**, следующие — функцией
  перехода. Поэтому история есть даже у задачи, которую никто не трогал, и её нельзя
  «забыть» написать.
- **История защищена в три слоя:** нет привилегий на `INSERT`/`UPDATE`/`DELETE`, политика RLS на
  вставку запрещена, поверх — триггеры, отклоняющие любую правку. Читается она только через
  функцию `task_history()`, которая проверяет, что задача видна спрашивающему.
- **Автор записи истории — автор задачи, а не сессия** при создании; в остальных случаях —
  тот, кто вызвал переход. Имя берётся из `profiles`.

## Что сделано не полностью

- **Удаление — жёсткое**, задачи и объекты уходят вместе с историей (`ON DELETE CASCADE`).
  Для рабочей системы я бы делал мягкое удаление/архив: ТЗ этого не требует, и история,
  которая исчезает вместе с задачей, — сознательная жертва объёму работы.
- **Нет тестов в CI.** Есть `scripts/verify.mjs` (проверки прав) и `scripts/setup.mjs`
  (данные проходят реальные переходы) — их нужно запускать руками. Playwright-тесты и GitHub
  Actions не делал.
- **Нет поиска, фильтров и пагинации** в списках: объём данных тестовый, таблицы на десятках
  строк выглядят нормально, на тысячах — потребуют серверной пагинации.
- **Нет real-time обновления** (у второй вкладки список не освежится сам), уведомлений о
  назначениях и возвратах на доработку, загрузки файлов и фото к задачам.
- **Нет ролей «на вырост»** (прораб, заказчик, только чтение) — две роли, как в ТЗ.
- **Деплой:** сборка статическая (`npm run build` → `dist`), для Vercel/Netlify достаточно
  указать Vite как фреймворк и две переменные окружения. Ссылка на развёрнутый проект —
  в письме с сдачей.
