# Мини-CRM «Объекты и задачи»

Система для строительной компании: руководитель ставит задачи по объектам (стройкам),
исполнители берут их в работу, отправляют на проверку; постановщик принимает работу или
возвращает на доработку. Каждой смена статуса попадает в историю задачи.

**Стек:** React 19 + TypeScript + Vite, Ant Design, Supabase (Auth + Postgres + RLS).
Права и правила переходов статусов живут в базе, интерфейс их только показывает.

## Быстрый старт

```bash
npm install
cp .env.example .env.local          # вписать URL проекта и anon-ключ
npm run dev                         # http://localhost:5173
```

Значения `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` берутся из
Supabase Dashboard → Project Settings → API. Это публичные значения: ключ `anon`
не даёт доступа к данным, дальше работают политики RLS.

### 1. Миграции базы

Вариант А — `npm run migrate`: скрипт сам читает ref проекта из `supabase/.temp/project-ref`
и пароль из `.env.local` (`SUPABASE_DB_PASSWORD`) и накатывает файлы по порядку через пулер.
Нужен он потому, что `npx supabase db push` на этой машине не работает: прямой хост
`db.<ref>.supabase.com` отдаёт только IPv6-адрес, а IPv6-маршрута нет, поэтому доступ
остаётся через пулер (он же требует закрепить сертификат Supabase — см. `certs/`).
Если IPv4 есть, обычный путь тоже подходит:

```bash
npx supabase link --project-ref <REF>
npx supabase db push
```

Вариант Б — руками: скопировать содержимое файлов `supabase/migrations/0001…0003`
по порядку в Dashboard → SQL Editor и выполнить.

### 2. Тестовые пользователи и данные

Открытая регистрация на проекте отключена, аккаунты создаёт скрипт (или админ через
Dashboard → Authentication). Нужен `SUPABASE_SERVICE_ROLE_KEY` из Project Settings → API —
он используется **только** в этом скрипте, из `.env.local`, и в браузер не попадает.

```bash
npm run setup
```

Скрипт создаёт одного постановщика и двух исполнителей, три объекта и пять задач,
а затем проходит цикл статусов через те же функции, что вызывает интерфейс.
Логины и пароли — в `.env.local` (`TEST_MANAGER_EMAIL` и т. д.), по умолчанию:

| Роль | Email | Пароль |
| --- | --- | --- |
| Постановщик | `manager@crm.test` | `Manager123!` |
| Исполнитель | `executor1@crm.test` | `Executor123!` |
| Исполнитель | `executor2@crm.test` | `Executor123!` |

### 3. Проверка безопасности

```bash
npm run verify
```

20+ проверок обращаются к Supabase напрямую, в обход интерфейса: чужие задачи,
запрещённые переходы статусов, подделка истории, доступ без токена.
Всё, что должно быть запрещено, подтверждается ошибкой от базы.

## Структура

```
supabase/migrations/   0001 схема · 0002 функции, переходы, RLS · 0003 профиль пользователя
src/lib/              клиент Supabase, сессия и роль, обёртки запросов
src/pages/            вход, объекты, карточка объекта, карточка задачи, мои задачи
src/components/       таблица задач, история, модальные формы, макет
scripts/              migrate.mjs — накатка миграций, setup.mjs — пользователи и данные,
                      verify.mjs — проверки прав в обход интерфейса
docs/                 объяснение для руководителя и список допущений
```

## Как устроены права (кратко)

- Роли (`manager` / `executor`) лежат в таблице `profiles`, которую пользователь не
  может редактировать: политик на `UPDATE` и `DELETE` нет вовсе.
- Постановщик видит и правит всё. Исполнитель видит только свои задачи и объекты,
  где они есть — это `can_see_task()` / `can_see_object()` в политиках RLS.
- Статус меняется только функцией `set_task_status()`. Она сверяет пару «текущий статус →
  новый» со справочником `task_transitions` и ролью вызывающего; для возврата на доработку
  требует комментарий. Прямой `UPDATE tasks.status` запрещён привилегией на колонку.
- История пишется той же функцией и триггером при создании задачи. Для неё разрешено
  только чтение, а `UPDATE`/`DELETE` отсекаются и отсутствием прав, и триггерами.

## Запуск на хостинге

Проект собирается статически (`npm run build` → `dist/`). На Vercel: Framework Preset —
Vite, переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, Build Command `npm run build`,
Output `dist`. `SUPABASE_SERVICE_ROLE_KEY` на хостинг не добавляется — приложению он не нужен.
